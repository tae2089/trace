# Trace v3: 프로토콜 독립적인 에러 추적 코어

## Problem Statement

Trace는 Go 에러의 발생 위치와 전달 경로를 추적하기 위한 패키지이지만,
v2까지 typed errors, HTTP 변환, slog, context helpers, generics, 시스템 에러
분류 등 애플리케이션마다 달라질 수 있는 의미와 정책까지 책임 범위에
포함하게 되었다. 이로 인해 패키지의 목적이 흐려지고, 특정 기능을 보완할
때마다 더 많은 정책과 호환 API가 필요해지는 문제가 생겼다.

사용자는 Trace가 에러의 의미를 결정하거나 처리 정책을 제공하기보다, 원래
에러를 보존하면서 어느 위치에서 발생했고 어떤 계층을 거쳐 전달됐는지를
신뢰성 있게 보여주는 작고 예측 가능한 도구이기를 원한다. 도메인 에러,
공개 에러 코드, HTTP나 gRPC 상태, 사용자 메시지, 로깅과 재시도 정책은
애플리케이션이 소유해야 한다.

## Solution

v3는 Trace를 프로토콜 독립적인 에러 추적 코어로 다시 정의한다. 공개 API는
`New`, `Errorf`, `Wrap`, `Wrapf` 네 함수로 제한하고, 공개 타입이나 검사용
보조 함수는 제공하지 않는다. 각 함수는 호출 위치를 기록하고, 래핑 함수는
필수 설명 문자열과 원래 원인을 보존한다.

사용자는 일반적인 `error` 값과 표준 `errors.Is`, `errors.As`,
`errors.Unwrap`만 사용한다. 일반 출력은 문맥과 원인 메시지만 보여주며,
`%+v`는 사람이 읽을 수 있는 디버그 표현으로 발생 위치와 전달 경로를
보여준다. typed errors와 프로토콜 매핑을 비롯한 모든 에러 의미와 처리
정책은 애플리케이션 또는 별도 라이브러리에서 구현한다.

v3는 먼저 `v3.0.0-rc.1`로 공개한다. Trace를 이미 사용하는 실제
애플리케이션인 `go-template`을 마이그레이션해 계약과 사용성을 검증한 뒤
`v3.0.0`으로 승격한다.

## User Stories

1. Go 개발자로서 원래 에러를 Trace로 감싸고 싶다. 그래야 원인을 잃지 않고 전달 위치를 기록할 수 있다.
2. Go 개발자로서 에러가 발생한 위치를 기록하고 싶다. 그래야 최초 발생 지점을 빠르게 찾을 수 있다.
3. Go 개발자로서 서비스 계층마다 설명 문맥을 추가하고 싶다. 그래야 에러가 어떤 작업 중 전달됐는지 이해할 수 있다.
4. Go 개발자로서 `errors.Is`로 sentinel error를 판별하고 싶다. 그래야 Trace를 사용해도 표준 Go 에러 처리 방식을 유지할 수 있다.
5. Go 개발자로서 `errors.As`로 애플리케이션 소유 에러 타입을 꺼내고 싶다. 그래야 도메인 정책을 Trace와 분리할 수 있다.
6. Go 개발자로서 `errors.Unwrap`으로 원인 체인을 순회하고 싶다. 그래야 Trace 전용 검사 API를 배울 필요가 없다.
7. Go 개발자로서 `Errorf`에서 `%w`를 사용하고 싶다. 그래야 `fmt.Errorf`에 익숙한 방식으로 원인을 보존할 수 있다.
8. Go 개발자로서 여러 `%w`로 연결된 원인을 유지하고 싶다. 그래야 표준 Go 다중 원인 에러와 상호 운용할 수 있다.
9. Go 개발자로서 `errors.Join`으로 만든 에러를 감싸고 싶다. 그래야 별도의 집계 에러 API 없이 표준 에러 트리를 사용할 수 있다.
10. Go 개발자로서 다중 원인 에러의 각 Trace 경로를 상세 출력에서 보고 싶다. 그래야 어느 분기에서 문제가 생겼는지 파악할 수 있다.
11. Go 개발자로서 일반 에러 문자열에는 스택이 나타나지 않기를 원한다. 그래야 사용자 응답과 평범한 로그가 파일 경로로 오염되지 않는다.
12. Go 개발자로서 `%+v`를 사용할 때만 함수, 파일, 줄 번호를 보고 싶다. 그래야 필요할 때 충분한 디버깅 정보를 얻을 수 있다.
13. Go 개발자로서 일반 출력에서 `문맥: 원인` 형태의 익숙한 메시지를 보고 싶다. 그래야 표준 래핑 에러처럼 읽을 수 있다.
14. Go 개발자로서 `Wrap`에 의미 있는 설명을 반드시 제공하고 싶다. 그래야 위치만 추가하는 빈 래퍼가 누적되지 않는다.
15. Go 개발자로서 nil 에러를 조건문 없이 `Wrap`이나 `Wrapf`에 전달하고 싶다. 그래야 nil이 그대로 유지된다.
16. 라이브러리 사용자로서 공개 API가 네 함수로 작게 유지되기를 원한다. 그래야 패키지의 역할과 사용법을 빠르게 이해할 수 있다.
17. 라이브러리 사용자로서 Trace 내부 타입에 의존하지 않기를 원한다. 그래야 내부 구현이 개선되어도 애플리케이션 코드가 영향을 받지 않는다.
18. 라이브러리 사용자로서 Trace가 외부 의존성을 추가하지 않기를 원한다. 그래야 작은 기반 패키지를 부담 없이 도입할 수 있다.
19. 성능에 민감한 개발자로서 에러 생성과 래핑 중에는 심볼 해석 비용을 내지 않기를 원한다. 그래야 상세 출력을 하지 않는 일반 경로가 가볍게 유지된다.
20. 유지보수자로서 성능 회귀를 벤치마크로 확인하고 싶다. 그래야 절대 수치를 성급하게 계약하지 않고도 변화의 영향을 판단할 수 있다.
21. 애플리케이션 개발자로서 도메인 에러 종류와 공개 코드를 직접 소유하고 싶다. 그래야 서비스 요구에 맞게 의미를 정의할 수 있다.
22. HTTP 애플리케이션 개발자로서 상태 코드와 응답 본문을 애플리케이션에서 결정하고 싶다. 그래야 Trace가 특정 프레임워크나 응답 정책을 강요하지 않는다.
23. 로깅 시스템 개발자로서 로그 레벨, 필드, 요청 ID와 메트릭을 애플리케이션에서 결정하고 싶다. 그래야 관측 정책과 에러 추적이 분리된다.
24. v2 사용자로서 제거된 기능이 왜 애플리케이션 책임으로 이동했는지 알고 싶다. 그래야 같은 기능을 Trace에서 다시 찾지 않고 올바르게 마이그레이션할 수 있다.
25. v2 사용자로서 typed errors, HTTP, slog, context helpers, generics의 간단한 전환 방향을 보고 싶다. 그래야 대체 라이브러리를 강요받지 않고 이전 작업을 시작할 수 있다.
26. 신규 사용자로서 README에서 순수한 에러 생성, 전달, 판별, 출력 흐름만 보고 싶다. 그래야 Trace의 목적을 잘못 이해하지 않는다.
27. 유지보수자로서 애플리케이션마다 달라질 수 있는 API 요청을 거절할 명확한 기준을 원한다. 그래야 v3의 범위가 다시 확장되지 않는다.
28. 기존 v2 사용자로서 심각한 오류와 보안 문제는 계속 수정되기를 원한다. 그래야 v3로 이전할 시간을 확보할 수 있다.
29. v3 도입자로서 RC에서 실제 애플리케이션 마이그레이션 결과를 확인하고 싶다. 그래야 정식 API가 현실적인 사용 흐름에서 검증됐음을 알 수 있다.
30. 릴리스 담당자로서 정식 v3 승격 조건을 알고 싶다. 그래야 코드 단위 테스트만 통과한 상태를 성급하게 안정 버전으로 선언하지 않는다.

## Implementation Decisions

- Trace의 공식 목적은 에러의 의미를 해석하거나 변경하지 않고, 에러가 어디서 발생해 어떤 경로로 전달됐는지를 추적하는 것이다.
- Trace가 소유하는 책임은 원인 보존, 설명 문맥 추가, 발생 및 전달 위치 기록, 사람이 읽는 디버그 출력으로 제한한다.
- 애플리케이션은 도메인 에러 타입과 분류, 공개 에러 코드, 프로토콜 상태, 응답 직렬화, 사용자 메시지, 재시도, 로깅, 메트릭, 요청 ID, 미들웨어와 panic recovery를 소유한다.
- 새 API가 프로토콜 독립적인 에러 추적을 직접 개선하지 않거나 애플리케이션마다 합리적으로 달라질 수 있다면 Trace에 추가하지 않는다.
- v3의 모듈 경로는 Go semantic import versioning에 따라 `/v3` 접미사를 사용하며 패키지 이름은 `trace`를 유지한다.
- 최소 Go 버전은 v2와 동일한 Go 1.25로 유지한다.
- 구현은 Go 표준 라이브러리에만 의존한다.
- 공개 API는 `New`, `Errorf`, `Wrap`, `Wrapf` 네 함수뿐이다. 공개 구조체, 인터페이스, sentinel, 프레임 타입, 조회 함수 또는 iterator는 만들지 않는다.
- `New`와 `Errorf`는 새 에러의 호출 위치를 기록한다.
- `Wrap`과 `Wrapf`는 원래 에러를 원인으로 보존하고 호출 위치를 전달 프레임으로 추가한다.
- `Wrap`은 설명 문자열을 필수로 받는다. 추가할 설명이 없다면 호출자는 원래 에러를 그대로 반환한다.
- `Wrapf`는 명시적으로 전달된 에러를 원인으로 삼고 형식화된 설명 문맥을 추가한다.
- `Wrap`과 `Wrapf`는 원래 에러가 nil이면 nil을 반환한다.
- `Errorf`는 표준 `fmt.Errorf`와 같은 `%w` 원인 연결을 지원한다. 하나 이상의 `%w`로 만들어진 표준 에러 트리도 보존한다.
- 모든 반환값은 표준 `error`로 다뤄지며 `errors.Is`, `errors.As`, `errors.Unwrap`의 의미를 변경하지 않는다.
- 각 Trace 래퍼는 자신의 원인과 한 개의 호출 위치를 내부적으로 보관한다. 외부에 누적 프레임 자료구조를 노출하지 않는다.
- 호출 시점에는 위치 식별값만 캡처하고 함수명, 파일명과 줄 번호의 심볼 해석은 상세 출력 시점까지 지연한다.
- 내부 에러 값은 생성 후 불변으로 취급해 여러 goroutine에서 안전하게 읽고 출력할 수 있게 한다.
- `Error()`, `%s`, `%v`는 스택 없이 설명 문맥과 원인 메시지를 일반적인 래핑 형태로 출력한다.
- `%+v`는 Trace가 기록한 각 발생 및 전달 위치를 함수, 파일, 줄 번호와 함께 출력한다.
- `%+v`는 `Unwrap() error`와 `Unwrap() []error`를 모두 따라가며 Trace가 기록된 다중 원인 분기를 빠뜨리지 않는다.
- 상세 출력은 결정적이고 테스트 가능해야 하지만 사람이 읽는 디버그 표현이다. 정확한 줄 배치, 구분자와 필드 순서는 기계가 파싱할 안정 API로 보장하지 않는다.
- 임의의 에러 구현이 비정상적인 순환 원인 체인을 제공하더라도 상세 출력이 무한 루프나 panic으로 이어지지 않도록 방어한다.
- README와 기본 예시는 에러 생성, 계층별 래핑, 표준 판별과 일반 및 상세 출력만 다룬다.
- 마이그레이션 문서는 제거된 v2 기능의 대체 구현을 제공하지 않는다. 대신 typed errors, HTTP, slog, context helpers, generics와 시스템 에러 분류가 애플리케이션 또는 별도 라이브러리 책임이라는 방향과 짧은 전환 예시를 제공한다.
- HTTP 예시는 기본 사용법이 아니라 마이그레이션 문서에서 애플리케이션 소유 어댑터의 예로만 제시한다.
- v2에는 새 기능을 추가하지 않으며 심각한 정확성 오류와 보안 문제만 수정한다.
- 첫 공개 버전은 `v3.0.0-rc.1`이다. RC 검증이 끝난 후에만 `v3.0.0`으로 승격한다.
- RC 검증 애플리케이션은 `go-template`로 확정한다. 이 마이그레이션은 typed errors, HTTP 매핑과 slog 정책이 애플리케이션으로 이동하는 실제 비용과 경계를 검증한다.

## Testing Decisions

- 주 테스트 seam은 외부 소비자와 동일한 `trace_test` 패키지에서 공개 API만 사용하는 black-box 테스트다. 내부 프레임 표현이나 helper 호출 여부가 아니라 관찰 가능한 에러 동작을 검증한다.
- 공개 API 감사는 exported surface가 네 함수로만 구성되는지 확인한다. 새 공개 심볼이 추가되면 의도적인 범위 결정 없이는 검증을 통과할 수 없어야 한다.
- `New`와 `Errorf`가 실제 호출 위치를 상세 출력에 기록하는지 검증한다.
- 여러 계층의 `Wrap`과 `Wrapf`가 각 호출 위치와 설명 문맥을 순서대로 보존하는지 검증한다.
- `Wrap(nil, ...)`과 `Wrapf(nil, ...)`가 nil을 반환하는지 검증한다.
- sentinel error와 사용자 정의 에러 타입을 대상으로 `errors.Is`, `errors.As`, `errors.Unwrap` 호환성을 검증한다.
- `Errorf`의 단일 `%w`와 다중 `%w`가 표준 원인 체인 및 트리 의미를 유지하는지 검증한다.
- `errors.Join`의 각 분기가 `errors.Is`와 `errors.As`로 발견되며 `%+v`에서도 Trace 경로를 잃지 않는지 검증한다.
- `Error()`, `%s`, `%v`에 파일, 함수와 줄 번호가 포함되지 않고 설명과 원인 메시지만 포함되는지 검증한다.
- `%+v`에 각 Trace 프레임의 함수, 파일과 줄 번호가 포함되며 동일한 에러에 대한 반복 출력이 결정적인지 검증한다.
- 정확한 전체 `%+v` 문자열을 장기 호환 계약으로 고정하는 과도한 snapshot은 피한다. 대신 필요한 문맥, 원인과 프레임의 존재 및 순서를 검증한다.
- 표준 단일 원인과 다중 원인 트리를 함께 사용해 상세 출력의 중복, 누락, 무한 순회와 panic을 검증한다.
- 사용자 정의 `error`와 `fmt.Formatter` 구현을 감쌌을 때 원인 판별과 일반 출력이 훼손되지 않는지 검증한다.
- 병렬 테스트와 race detector로 생성 후 불변인 에러의 동시 출력 및 판별 안전성을 검증한다.
- 기존 벤치마크 seam을 활용해 생성, 한 단계 래핑, 깊은 래핑, 일반 출력과 `%+v` 비용을 비교한다. 절대 시간이나 할당 수를 공개 계약으로 삼지 않고 회귀 판단 자료로 기록한다.
- 심볼 해석 지연은 일반 생성 및 래핑 벤치마크와 `%+v` 벤치마크의 비용 차이로 확인한다.
- 두 번째 출시 seam은 `go-template`의 실제 마이그레이션이다. 서비스와 저장소 계층의 래핑, 애플리케이션 에러 판별, HTTP 응답 매핑, slog 출력, 빌드와 전체 테스트를 검증한다.
- `v3.0.0` 승격에는 Trace 자체의 테스트, race 검사와 벤치마크 검토뿐 아니라 `go-template` 마이그레이션 및 테스트 통과가 필요하다.
- v2의 기존 테스트는 v3에 그대로 이식하지 않는다. 새 책임 경계에 포함되는 원인 보존, 프레임 누적, 포매팅과 표준 에러 상호 운용 테스트만 prior art로 활용한다.

## Out of Scope

- Trace가 정의하는 typed error, 에러 category, predicate 또는 retryable 의미
- `StatusCode`, `CodedError`와 같은 정책 확장 인터페이스
- HTTP 상태 변환, 요청 및 응답 구조, 안전한 응답 생성과 읽기, 클라이언트 wrapper 또는 middleware
- gRPC 코드, CLI 종료 코드와 기타 프로토콜 매핑
- 구조화 필드, slog handler, 로그 레벨과 로그 스키마
- context 값, trace ID, cancellation 또는 deadline helper
- `Result`, `Pipeline`과 기타 generics workflow
- 시스템 에러 및 errno 분류
- 별도의 aggregate error 또는 error iterator
- 공개 `TraceError`, `Frame`, `GetFrames`, `Inspect`, `DebugReport`와 기타 내부 검사 API
- 사용자 메시지 선별, 민감 정보 제거 또는 공개 응답 정책
- panic recovery, 메트릭, request ID와 route metadata
- `%+v` 출력의 기계 판독 스키마나 장기적으로 고정된 텍스트 형식
- 제거된 v2 기능을 대체하는 별도 라이브러리의 설계와 구현
- v2의 일반 기능 개선 또는 v3 기능 backport
- Go 1.24 이하 지원 확대
- 이 명세를 구현 티켓으로 분해하는 작업

## Further Notes

- v3는 v2의 기능 동등성이나 `gravitational/trace`와의 API 유사성을 목표로 하지 않는다. 성공 기준은 더 많은 기능이 아니라 더 선명한 책임 경계다.
- 표준 Go 에러 체인은 Trace와 애플리케이션 사이의 유일한 통합 계약이다. 애플리케이션은 Trace로 감싼 에러를 자체 어댑터에서 자유롭게 판별할 수 있어야 한다.
- Trace가 기록하기 전에 생성된 외부 에러의 실제 발생 위치는 알 수 없다. 이 경우 첫 Trace 호출 위치부터 기록하며 존재하지 않는 origin을 추정하지 않는다.
- RC 단계에서 발견된 문제 중 네 공개 함수의 의미를 바꾸는 사항은 정식 출시 전에 해결한다. 단순한 디버그 출력 배치 개선은 기계 판독 계약으로 취급하지 않는다.
- `go-template` 마이그레이션은 검증 작업이며 Trace가 애플리케이션 정책을 다시 소유하는 근거로 사용하지 않는다.
- 후속 작업 분해가 필요할 때는 이 명세를 입력으로 `to-issues`를 별도로 실행한다.
